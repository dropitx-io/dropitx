## Spacing Scale

Declared values (must be multiples of 4), matching Tailwind's default 4px base grid already used throughout `favorites/page.tsx`, `search/page.tsx`, `teams/page.tsx`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge padding |
| sm | 8px | Compact element spacing (`gap-2`, badge row gaps) |
| md | 16px | Default element spacing (`gap-4`, card padding `p-4`) |
| lg | 24px | Section spacing (`space-y-6`, page header-to-content gap) |
| xl | 32px | Layout gaps (`p-8` dialog padding, empty-state icon well) |
| 2xl | 48px | Major section breaks (`size-12` icon wells, `size-16` avatars) |
| 3xl | 64px | Page-level spacing (`py-16` empty-state vertical padding) |

**Exceptions — scope restricted to specific pre-existing, unmodified code this phase does not touch:**
- `favorites/page.tsx` and `badge.tsx` (both **unmodified** by this phase) may keep their existing half-step values (`gap-1.5` = 6px, `mt-3.5` = 14px, `px-2.5` = 10px — Tailwind's standard 0.25rem-step scale, not arbitrary) exactly as already shipped. This phase does not restyle those call sites, so they are out of scope for the strict 4/8/16/24/32/48/64 rule.
- **This phase's own new/modified surfaces — Explore, Public Profile, Custom Domains, File Requests pages, the Stars toggle (`bookmark-toggle.tsx`) changes, and the Encryption action UI — must use ONLY the declared 4/8/16/24/32/48/64 scale above.** No `.5`-suffixed Tailwind spacing utility (e.g. `gap-1.5`, `mt-3.5`, `px-2.5`) may be introduced on any of these six surfaces, even where an existing page nearby uses one.
- Exception to the exception: the shadcn `Badge` primitive (`components/ui/badge.tsx`, **not modified this phase**) ships with baked-in internal padding (`px-2.5 py-0.5`) that this phase reuses unmodified for file-type badges (Explore) and status badges (Custom Domains, File Requests). This is inherited primitive styling, not new spacing authored by this phase — same treatment as the `CardTitle` weight note in Typography below — and does not violate the strict scale above.
- Icon-only buttons (Stars toggle, Copy button) use `icon-sm` (32px) / `icon` (36px) from `button.tsx` — both multiples of 4, but below the 44px WCAG touch-target recommendation. This is an existing app-wide `button.tsx` variant (not introduced by this phase); reusing it on the Stars toggle keeps it visually consistent with every other icon button in the app. Flag as a candidate for a future accessibility pass (Phase 3/SEC scope), not this phase's fix.

## Typography

Declared for this phase's new/modified UI (mirrors sizes already in production use on `favorites/page.tsx`, `search/page.tsx`, `teams/page.tsx` — do not invent new sizes):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Page heading (h1) | 22px (`text-[22px]`) | 700 (bold) | 1.2 |
| Section/card title | 16px (`text-base`, shadcn `CardTitle` default) | *out of scope — see note below* | 1.3 |
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Meta/label/caption | 12px (`text-xs`) | 400 (regular) | 1.4 |

**Exactly 4 sizes (22/16/14/12px) and exactly 2 weights are declared by this contract: 400 (regular) for Body and Meta/label/caption, and 700 (bold) for the Page heading.** Meta/label/caption is standardized on 12px (`text-xs`) only — the pre-existing `text-[11px]` used in `favorites/page.tsx` metadata rows is a call site this phase does not touch and is not part of this phase's declared scale; do not introduce `text-[11px]` on any new/modified surface.

The shadcn `CardTitle` primitive's built-in font weight is a primitive default this phase inherits unchanged wherever `CardTitle` is reused (Explore cards, Public Profile cards) — it is **not** a weight this contract declares or a value the executor should treat as part of the 2-weight scale. Do not add new `font-semibold`/`font-medium` treatments to any new copy beyond what `CardTitle` already applies out of the box, and do not override `CardTitle`'s default weight.

## Copywriting Contract

Per-surface, since this phase touches six distinct UI surfaces (Stars toggle, Encryption action, Explore, Public Profile, Custom Domains, File Requests). Empty/error states use existing app tone: short, declarative, one supporting sentence.

| Surface | Primary CTA | Empty state heading | Empty state body | Error state | Destructive confirmation |
|---------|-------------|---------------------|-------------------|--------------|---------------------------|
| Stars toggle (`bookmark-toggle.tsx`) | n/a (icon toggle, not a CTA) — icon + count label, e.g. `★ 12` | n/a | n/a | Silent revert on failure (existing pattern) — keep as-is, no new toast; do not over-build error UI for a lightweight toggle | n/a (not destructive — un-starring is reversible, no confirmation needed) |
| Explore (`app/(public)/explore`) | "Browse shares" (page has no single form CTA — filter/tab switch is the primary interaction) | "Nothing here yet" | "No public shares match this filter. Try Trending or clear your tags." | "Couldn't load Explore. [Retry]" | n/a |
| Public Profile (`app/u/[username]`) | n/a (read-only page) | "No public shares yet" | "When {username} shares something publicly, it'll show up here." *(Note: this copy is written to read as a normal, unremarkable empty state — a known backend bug (CONTEXT.md, Pitfall 3) makes every profile's share list return empty regardless of actual content; do not word this as "coming soon" or anything that would look broken once the bug is fixed and shares do appear)* | "Couldn't load this profile. [Retry]" | n/a |
| Custom Domains (dashboard) | "Add Domain" | "No custom domains yet" | "Add a domain to serve your shares from your own URL." | "Verification failed — check your DNS records and try again." (inline per-domain, not a global toast) | "Remove Domain": "Remove {domain}? Shares using it will fall back to the default dropitx.site URL." |
| File Requests — dashboard mgmt (`app/(dashboard)/dashboard/requests`) | "Create Request" | "No file requests yet" | "Create a request to let anyone upload files to you without an account." | "Couldn't load requests. [Retry]" | "Delete Request": "Delete this request? Anyone with the link will no longer be able to upload." |
| File Requests — public upload (`app/(public)/requests/[slug]`) | "Upload Files" | n/a (form, not a collection) | n/a | "Upload failed — check your connection and try again." / "This request is no longer accepting uploads." (closed/expired state) | n/a (anonymous uploader has nothing to delete) |
| Encryption action (share settings) | "Encrypt This Share" (distinct button/menu item from the existing "Set Password") | n/a | n/a | "Encryption failed. Your content was not changed." | "Re-encrypt": "Re-encrypting replaces the current password. Anyone using the old password will lose access — this cannot be undone." *(mandatory copy — see UI Considerations; ties to the unauthenticated-reencrypt backend gap)* |

**Labeling rule (locked by CONTEXT.md D-encryption decision):** "Set Password" (existing `share-password-form.tsx`/`password-gate.tsx`) and "Encrypt This Share" (new) must appear as two visually and textually distinct actions in the same UI area (e.g., two separate buttons/menu rows in share settings, not a toggle or tab that implies they're the same feature). Use a different icon for each: existing `Lock` for Set Password, `ShieldCheck` (new, Lucide) for Encrypt — never reuse the same icon for both.

| populated | Explore results grid | ✅ covered | Reuse `favorites/page.tsx`'s card grid exactly: `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`, `rounded-[22px]` card, `clay-raised` |
| populated | Public Profile shares list | ✅ covered | Same card grid pattern as Explore/Favorites for visual consistency across all "list of shares" surfaces in the app |
| populated | Custom Domains list | ✅ covered | Row-based list (not a card grid) — one row per domain with status badge (`Badge` variant `success`/`warn`/`danger` for verified/pending/failed), matching `teams/page.tsx`'s member-row convention more than the card-grid convention (domains are administrative rows, not shareable content cards) |
| populated | File Requests dashboard list | ✅ covered | Same row-based list convention as Custom Domains (administrative list, not content cards) |
| zero-one-many | Stars count label | ✅ covered | Singular/plural not needed — count is always a number (`★ 0`, `★ 1`, `★ 12`), no pluralized noun attached, avoiding the singular/plural copy problem entirely |
| zero-one-many | Public Profile stats row (share_count/total_views/total_stars) | 🧪 backstop | Given the known backend bug returns 0 for all three regardless of actual data (CONTEXT.md Pitfall 3), the UI cannot be verified against real nonzero data this phase. Executor must confirm the stats row renders sanely at `0/0/0` (not visually broken) as a held-out check; true nonzero rendering is unverifiable until the cross-repo bug is fixed — flag, don't silently assume it "just works" at scale |
| overflow | Custom Domains list (long domain names) | ✅ covered | `truncate` on the domain-name cell, matching the existing truncate pattern in `favorites/page.tsx`'s card title (`truncate`) |
| overflow | File Requests list (long request titles/descriptions) | ✅ covered | Same `truncate` treatment for titles; descriptions clamp to 2 lines (`line-clamp-2`, a new but standard Tailwind utility, safe to introduce) |
| long-text | Public Profile bio (static-content) | ✅ covered | `line-clamp-3` with no "read more" expansion in this phase (out of scope — simple clamp is sufficient per CONTEXT.md's "no specific visual references" allowance for Claude's discretion) |

| partial | Custom Domains — domain added but verification pending | 🧪 backstop | UI must render a distinct "Pending verification" badge state (`Badge` variant `warn`) between "just added" and "verified" — this is a real intermediate state the backend supports (`verify_domain` workflow) but wasn't manually exercised this research session; executor should smoke-test the pending state, not assume the badge renders correctly on first try |
| partial | File Requests — request created but zero uploads received yet | ✅ covered | Distinguish this from the list-level "no requests yet" empty state — an individual request with 0 uploads shows "No uploads yet" inline on its row/detail, not the page-level empty state copy |
| long-text | Encrypt dialog password/confirmation fields (form) | ⚠ unresolved | No character-limit or strength-meter UX was discussed with the user (CONTEXT.md's `<specifics>` explicitly notes no visual references given); planner should treat "no password strength meter, no explicit max-length UI" as an assumption unless a later decision adds one |
