<objective>
Complete D-01's second half: cut the favorites *list* page over to Stars, retiring the frontend-native `favorites` table as the source of truth. Plan 01.1-01 already migrated the *toggle* half, which had no dependencies and shipped independently.

This half cannot ship independently. It requires a backend endpoint that does not exist, and it makes an existing table's data invisible to users. Both need an explicit human decision before any code is written.

Purpose: leaving the toggle on Stars while the list page still reads the old `favorites` table would produce the worst possible state — a user stars something and it never appears in their favorites list. That inconsistency is the reason this plan exists rather than being deferred.
Output: either a completed cutover, or a clean, documented stop with the blocker recorded.
</objective>

D-01 locked the direction: migrate to Stars, retire the frontend `favorites` table as source of truth. Plan 01.1-01 already shipped the toggle half against the live per-share Stars endpoints. This page is the remaining half, and two facts block it.

**Fact 1 — the endpoint does not exist (D-01a, verified 2026-08-16).** `dropitx-api/app/public/stars.py` contains exactly three routes: `GET`, `POST`, and `DELETE /api/shares/{slug}/star`. There is no "list the shares this user has starred" endpoint anywhere in `dropitx-api` — confirmed by grepping `dropitx-api/app` for `starred`, `list.*star`, and `user_stars`, which returned zero hits beyond those three routes. This page needs precisely that endpoint. Adding it is **cross-repo work in `dropitx-api`'s own codebase and roadmap**; this phase's planning lives in `dropitx/` and its executor must not write Python here. CONTEXT.md notes a peer session may already be active on `dropitx-api` and can carry the request.

**Fact 2 — existing user data becomes invisible.** The current page reads `favorites` rows keyed by `user_id` from this repo's own Supabase project. Those rows were never written to `share_stars` — different table, different database (`dropitx-api` runs its own local Postgres; see RESEARCH.md Assumption A2). Cutting the page over without a backfill means every user who has ever favorited something opens this page to an empty list, with no notice and no way to recover the list themselves. No row is deleted, but from the user's perspective the data is gone.

**Fact 3 — the intermediate state is already live.** Plan 01.1-01 shipped. Right now the toggle writes to `share_stars` while this page reads `favorites`, so newly starred shares do not appear here. That inconsistency exists from the moment 01.1-01 lands and persists until this plan resolves.
