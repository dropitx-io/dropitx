**Signal — "profile" now has two write concerns: a frontend-only route vs. a backend one.**
Outcome: **add-alongside, accepted debt** — already decided in CONTEXT.md D-02, recorded here explicitly rather than implied.

Two distinct `user_profiles` tables exist with the same name in two different databases: this repo's Supabase project (written by the new `PUT /api/profile`, read by `/dashboard/profile`) and `dropitx-api`'s own local Postgres (read by `GET /api/auth/session` and by `GET /api/u/{username}`). This plan does **not** unify them and does not attempt to. The accepted consequence: a display name saved in the dashboard will **not** appear on that user's public profile page built in plan 01.1-07, because those two surfaces read different databases. This is recorded as a known limitation, is listed in CONTEXT.md `<deferred>` as a candidate for a future ADR, and must be restated in this plan's SUMMARY so plan 01.1-07's executor does not treat the divergence as a bug they introduced.
</assumption_delta_decision>

    - Unauthenticated request (no valid `session` cookie) -> 401 `{ error: "Unauthorized" }`, no Supabase call made.
    - Body is not valid JSON -> 400 `{ error: "display_name is required" }`.
    - `display_name` missing, not a string, or trims to empty -> 400, no write.
    - `display_name` of 250 characters -> stored value is exactly the first 100 characters after trim.
    - Valid request -> 200 `{ ok: true }` and the row whose `user_id` equals the session uid has the new `display_name`.
    - Body containing a `user_id` field different from the session uid -> that field is ignored; the write still targets the session uid's row.
    - Supabase returns an error -> 500 `{ error: "Failed to update profile" }`.
  </behavior>
  <action>
D-02: create `app/api/profile/route.ts` as a frontend-only Next.js Route Handler — NOT a new `dropitx-api` endpoint — writing to this repo's own Supabase `user_profiles` table via `createAdminClient()`, following the `app/api/shares/*` access-cookie precedent.

Export an async `PUT(request: NextRequest)` handler. No other HTTP method is exported.

Sequence:
1. `const cookieStore = await cookies()` then `const user = await getSessionUser(cookieStore)`. If falsy, return `NextResponse.json({ error: "Unauthorized" }, { status: 401 })` and return before constructing any Supabase client.
2. `const body = await request.json().catch(() => null)`. Narrow `body?.display_name` with a `typeof === "string"` check, then `.trim().slice(0, 100)`. If the result is empty, return `NextResponse.json({ error: "display_name is required" }, { status: 400 })`.
3. `const admin = createAdminClient()`, then `.from("user_profiles").update({ display_name: displayName }).eq("user_id", user.uid)`. The row selector is the session uid and nothing else.
4. On a Supabase `error`, return `NextResponse.json({ error: "Failed to update profile" }, { status: 500 })`. Otherwise `NextResponse.json({ ok: true })`.

Imports: `NextRequest`/`NextResponse` from `next/server`, `cookies` from `next/headers`, `createAdminClient` from `@/utils/supabase/server`, `getSessionUser` from `@/lib/firebase/server`. Do not import `authFetch` or `getApiUrl` — this route never calls the FastAPI backend (D-02).

TypeScript strict mode is enforced and `any` is banned: type the parsed body as `unknown` and narrow it, or declare a local `interface ProfileUpdateBody { display_name?: unknown }` and narrow from there.
