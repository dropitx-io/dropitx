# Phase 01.1: API Integration Migration - Context

**Gathered:** 2026-08-16
**Status:** Ready for planning

<domain>
## Phase Boundary

The frontend's API integration must match the live `api.dropitx.site` backend exactly — no broken calls, and every backend capability reachable from the UI. This phase is verify/fix/wire across two repos, not new-feature-building: the backend (`dropitx-api`) already implements almost everything needed; the gap is which paths the frontend calls and whether UI surface exists at all. See `01.1-RESEARCH.md` for full findings — this file captures the decisions made on top of that research.

</domain>

<decisions>
## Implementation Decisions

### Favorites (API-02)
- **D-01:** Migrate to Stars. Retire the frontend's own `favorites` table/page as the source of truth. Cut over `bookmark-toggle.tsx` to `GET/POST/DELETE /api/shares/{slug}/star` (response shape `{ starred: boolean, count: number }`, differs from the old `{ favorited: boolean }` shape — update callers accordingly). Cut over `app/(dashboard)/dashboard/favorites/page.tsx` to read starred shares via the Stars API instead of `.from("favorites")` direct Supabase reads.
- Rationale: lower total effort (reuses tested, deployed backend code), and closes the two-disconnected-databases gap for this concept (see Research §Assumptions Log A2 — `dropitx-api` uses its own local Postgres; the frontend's direct-Supabase favorites read was structurally cut off from it).
- **D-01a (cross-repo dependency, verified 2026-08-16):** `dropitx-api/app/public/stars.py` has ONLY per-share endpoints (`GET/POST/DELETE /api/shares/{slug}/star`) — no "list all shares the current user has starred" endpoint exists anywhere in `dropitx-api`. The favorites LIST page (`favorites/page.tsx`) needs exactly that. Confirmed by direct grep of `dropitx-api/app` for `starred`/`list.*star`/`user_stars` — zero hits beyond `stars.py`'s 3 existing routes.
- **Decision:** add one minimal new backend endpoint (e.g. `GET /api/me/stars` or `GET /api/users/me/starred-shares`) to `dropitx-api`, returning the current user's starred shares list. **This is a cross-repo, out-of-this-frontend-repo dependency** — `.planning/` for this roadmap lives in `dropitx/`, but the endpoint must be added to `dropitx-api`'s own codebase/roadmap. The planner for THIS phase must NOT attempt to write Python/FastAPI code — it should:
  1. Wire `bookmark-toggle.tsx`'s toggle against the existing per-share endpoints now (no dependency, ships independently).
  2. Add a task/checkpoint for `favorites/page.tsx`'s list-page cutover that explicitly depends on the new `dropitx-api` list endpoint existing — mark it blocked/gated on that cross-repo work landing, with acceptance criteria phrased as "once `GET /api/me/stars` (or equivalent) exists and is deployed to `api.dropitx.site`, wire `favorites/page.tsx` to call it via `authFetch`."
  3. Flag this explicitly in the plan's risk/dependency section so it isn't silently attempted as in-repo work.
- The user was informed a peer session may already be active on `dropitx-api` and can relay this need there if they choose — not automatically actioned by this session.

### Profile writes (API-02)
- **D-02:** Next.js Route Handler (frontend-only), NOT a new `dropitx-api` endpoint. Add a server-side write route (e.g. `app/api/profile/route.ts`) using `createAdminClient()` to write to the frontend's own existing `user_profiles` table in its own Supabase project — same repo-boundary precedent as the existing `app/api/shares/*` access-cookie routes.
- **Known tradeoff, accepted:** this keeps profile data on the frontend's own Supabase project, which is a *separate database* from what `api.dropitx.site` reads (`GET /api/auth/session`'s `profile` object comes from `dropitx-api`'s own local Postgres `user_profiles` table — a different table with the same name). Do not assume these two `user_profiles` tables are in sync; do not write code that reads one and expects the other's data. This split is accepted for this phase, not resolved — flag it as a candidate for a future phase/ADR if it causes visible inconsistency (e.g. profile shown in the dashboard vs. profile shown on a public `/api/u/{username}` page could diverge, since the public endpoint reads `dropitx-api`'s Postgres while the dashboard write in this phase targets the frontend's Supabase).
- **D-03 (bug fix, locked regardless of D-02):** Fix `app/(dashboard)/dashboard/profile/page.tsx`'s read query — `.eq("id", user.uid)` → `.eq("user_id", user.uid)` (see Research §Code Examples). This is a contained, independent bug; fix it in this phase no matter which write-path option is chosen.

### Upload/batch + file listing (API-05)
- **D-04:** Wire both `/api/upload/batch` (distinct group-upload feature, pairs with already-planned bulk-download-group UI) AND `GET /api/shares/{slug}/files` (file listing within one multi-file share) in this phase.
- **Cross-phase note (write this into Phase 4's eventual CONTEXT.md/RESEARCH.md when that phase is planned):** `GET /api/shares/{slug}/files` will already be wired by this phase (01.1) by the time Phase 4 (FEAT-03, multi-file backend wiring) is planned — Phase 4 should treat file *listing* as done and focus on file *organization* UI (rename/reorder/delete within a multi-file share) to avoid duplicate work.

### Encryption (API-04)
- Wire the existing, unwired `lib/crypto.ts` module against `/api/encryption/*`. This is **additive**, not a replacement for the existing `set-password`/`unlock` flow (`password-gate.tsx`, `share-password-form.tsx`) — those stay as-is. Ship "password-protect" (existing gate) and "encrypt" (new, true zero-knowledge encryption) as distinct, clearly-labeled UI actions unless a later explicit decision unifies them. See Research §Common Pitfalls #2 for why conflating them would break the existing password-gate feature.

### Backend bugs found during research — flag, do not fix here
- `dropitx-api/app/public/profiles.py` uses `user_profiles.id` instead of `user_profiles.user_id` when filtering `public_shares` — public profile pages will show `share_count: 0` etc. even once correctly wired. Cross-repo, out of this phase's edit scope per REQUIREMENTS.md's "no backend rewrites" exclusion. Document as a known limitation on API-04's public-profile success criterion; do not silently patch `dropitx-api` from this phase.
- `dropitx-api`'s `reencrypt_share` endpoint has no authorization check at all (anyone who knows the old password can re-encrypt with a new one, locking out the owner). Not this phase's fix (security hardening is Phase 3 scope) — but since this phase gives the encryption UI its first real, reachable entry point, add a `checkpoint:human-verify` acknowledging the gap before shipping the encrypt UI, rather than silently exposing it.

### Environment/deploy checks (API-01)
- Treat `curl https://api.dropitx.site/health` as the first task of execution — a live smoke test, not an assumption that the backend's recent Firebase-migration fixes are deployed.
- `NEXT_PUBLIC_API_URL` per-Vercel-environment correctness could not be verified this session (env access is privacy-blocked in this environment) — add an explicit `checkpoint:human-verify` task against the Vercel dashboard rather than a code-only check.

### Claude's Discretion
- Exact new-page layouts for Explore, Public Profiles, Custom Domains, File Requests (no design decisions were discussed — build to match existing dashboard/public page conventions).
- Whether Explore/Profiles/Domains/File-Requests become one plan each or are grouped — planner's call based on granularity settings.
- Order of task execution within a wave, beyond the "contained bugs first" sequencing recommended in research.

</decisions>

## Existing Code Insights

### Reusable Assets
- `lib/api-client.ts`'s `authFetch`/`getApiUrl` — already correct (Firebase bearer token + 401 retry). Every new endpoint group in this phase routes through this, never a bespoke fetch.
- `lib/crypto.ts` — already implements the exact AES-256-GCM/PBKDF2/URL-fragment-key contract `/api/encryption/*` expects. Do not build a new crypto module.
- `bookmark-toggle.tsx`'s existing pattern is the template for the Stars swap (same props already available: `shareId`, `slug`).

### Established Patterns
- `app/api/shares/*` access-cookie routes are the existing precedent for D-02's frontend Route Handler approach.

### Integration Points
- `BookmarkToggle` (favorites→Stars), `ProfileForm`/`dashboard/profile/page.tsx` (profile bug fix + new write route), `upload-dropzone.tsx` (batch upload), new routes for Explore/Public Profiles/Custom Domains/File Requests.
