# Phase 01.1: API Integration Migration - Research

**Researched:** 2026-08-16
**Domain:** Frontend-to-backend API contract alignment (Next.js `authFetch`/`getApiUrl` callers vs. live FastAPI `api.dropitx.site`, 84-endpoint OpenAPI spec)
**Confidence:** HIGH — every claim below was verified by reading the actual current source in both `dropitx/` (this repo) and `../dropitx-api` (sibling backend), not inferred from the OpenAPI spec alone. No CONTEXT.md exists for this phase; there are no locked user decisions to honor — this file also surfaces several decisions the planner/user must make explicitly before or during planning (see Assumptions Log and Open Questions).

## Summary

This phase is a **verify/fix/wire phase across two repos**, not new-feature-building. The live backend (`dropitx-api`) has already been substantially built out — 84 endpoints across 17 tag groups — and has *itself* recently migrated its auth mechanism from Supabase JWT to Firebase ID tokens (confirmed via `../dropitx-api/.planning/phases/02-firebase-auth-migration-completion/02-RESEARCH.md`, dated one day before this research). The frontend's `authFetch`/`getApiUrl` pair in `lib/api-client.ts` already implements the correct Firebase-bearer-token + 401-retry pattern; the gap is entirely in *which paths* frontend components call and whether backend routes for those UI surfaces exist at all.

Three findings materially change the phase's shape from what the task description assumed:

1. **`/api/v1/favorites` has no backend analog of any kind** — not a wrong path, not a renamed route. `grep -ril "favorite" app core models` inside `dropitx-api` returns **zero matches**. The closest functional equivalent is the fully-built **Stars** feature (`share_stars` table, `get_star_count`/`has_user_starred` RPCs, `GET/POST/DELETE /api/shares/{slug}/star`) — but this is a *different table* than the one the frontend's own `favorites` dashboard page already reads directly from Supabase. Fixing `bookmark-toggle.tsx` requires **both** a call-site swap **and** a decision about what happens to the pre-existing `favorites` table/page (see Open Questions).
2. **`/api/v1/profile` has no write path anywhere** — `GET /api/auth/session` (Firebase's provision-and-fetch endpoint) returns the full profile shape (`user_id, username, display_name, bio, avatar_url, is_public, created_at, updated_at`), but no PATCH/PUT endpoint updates `user_profiles` exists in `dropitx-api` at all (verified via exhaustive grep of `user_profiles` writes). This is a genuine gap requiring a scope decision, not a path typo.
3. **The frontend's own profile-read query is separately broken** — `app/(dashboard)/dashboard/profile/page.tsx` queries `.eq("id", user.uid)` on `user_profiles`, but `user_profiles.id` is a random `UUID` PK (`infra/init/01_schema.sql:299`) while `user_profiles.user_id` (`TEXT`, `infra/init/01_schema.sql:300`) is the actual Firebase-uid foreign key. This query currently returns no row (or a Postgres type error) for every user — a pure frontend bug, unrelated to the live-API-contract question, that must be fixed regardless of how the write-path decision lands.

For the ~10 "never wired" endpoint groups, effort varies enormously: **Stars** is a one-line swap (mirrors the existing `bookmark-toggle.tsx` pattern exactly). **Explore, Public Profiles, Custom Domains, and File Requests** all require *brand-new pages/routes* (no `app/(public)/explore`, `app/u/[username]`, or dashboard domains/requests directory exists today) — these are multi-file UI builds, not just hook wiring. **Encryption** is the most subtle: the frontend already has a fully-built, contract-matching client-side crypto module (`lib/crypto.ts`) that implements the exact AES-256-GCM + PBKDF2 + URL-fragment-key pattern the backend's `/api/encryption/*` group expects — it is simply never called. **Publish** (`/api/publish`, `PUT /api/publish/{slug}`) is *already wired* (`components/editor-publish-bar.tsx`), separate from and complementary to `/api/v1/documents` (API-key-authenticated CLI/API path) — API-05's "publish" language refers to confirming this existing wiring is correct, not building it. **Upload** is mostly done too: `/api/upload` and `/api/upload/multi` are wired in `upload-dropzone.tsx`, `/api/images/upload` is wired in `editor-shell.tsx` — only `/api/upload/batch` (a *distinct* group-upload feature, not a duplicate of `/multi`) and `/api/shares/{slug}/files` remain unwired. **CLI upload** (`/api/cli/upload*`) is confirmed out of scope — consumed by the separate `dropitx-cli` tool, not this Next.js app.

**Primary recommendation:** Sequence the phase as (1) fix the two confirmed frontend bugs (profile page's wrong column, `share-page-client.tsx`'s relative-fetch bug) first since they're contained and zero-risk; (2) resolve the favorites/profile-write architectural questions via `checkpoint:human-verify` or explicit user decision before writing any code for API-02, since both have multiple valid resolutions with real tradeoffs; (3) wire Stars (trivial, mirrors existing pattern); (4) wire Encryption (moderate — UI + calling existing crypto module against existing backend); (5) treat Explore/Profiles/Domains/File-Requests as their own sub-plans (new pages, larger surface) with `PLANNING.md` prioritizing per REQUIREMENTS.md's API-03/API-04 split; (6) confirm-only pass on Publish/Upload/CLI (verify, do not rebuild).

### Pattern: `authFetch`/`getApiUrl` call-site swap (Stars example)

**What:** Replace a 404ing path with the live equivalent, keep the same component shape.
**When to use:** Any endpoint where the "broken" call and the "correct" call have a structurally similar request/response shape (this phase's Stars fix, not its Explore/Domains new-page work).
**Example — current (broken) vs. target:**

```typescript
// Source: components/bookmark-toggle.tsx:29 and :57 (read this session) — CURRENT, 404s
authFetch(`/api/v1/favorites/${shareId}`)                          // GET — check status
authFetch(`/api/v1/favorites/${shareId}`, { method: prev ? "DELETE" : "POST" })
```

```typescript
// Source: app/public/stars.py:39-172 (read this session) — TARGET, live and tested
// Response shape differs: { starred: boolean, count: number } not { favorited: boolean }
authFetch(`/api/shares/${slug}/star`)                               // GET
authFetch(`/api/shares/${slug}/star`, { method: prev ? "DELETE" : "POST" })
```

`BookmarkToggle` already receives both `shareId` and `slug` as props (`app/(public)/s/[slug]/page.tsx:242` `[VERIFIED: app/(public)/s/[slug]/page.tsx:242, read this session]` — `<BookmarkToggle shareId={share.id} slug={share.slug} />`), so no prop plumbing is needed for the swap itself — only the favorites-table decision (Open Questions #1) affects total scope.

### Pattern: Encryption wiring using the existing client crypto module

**What:** `lib/crypto.ts` already implements `generateRandomKey`, `deriveKeyFromPassword`, `encrypt`/`decrypt`, `setKeyInFragment`/`getKeyFromFragment` — exactly matching the backend's zero-knowledge design (key never sent to server, only IV+salt persisted).
**When to use:** Wiring the "password-protect this share with encryption" UI action.
**Example (conceptual — no existing call site to point to; this is genuinely unwired):**

```typescript
// Backend contract, verified via app/public/encryption.py:105-149 (read this session)
// POST /api/encryption/generate-key → { key, iv, salt } (all base64url)
// POST /api/shares/{slug}/encrypt   → body: { password, delete_token? }
//                                      → { slug, encrypted, encryption_iv, encryption_salt, share_url }
// GET  /api/shares/{slug}/encryption-info → { encrypted, encryption_iv, encryption_salt, has_password }
```

**Do not conflate this with the existing `set-password`/`unlock` flow** (`components/share-password-form.tsx:36`, `components/password-gate.tsx:33`, both already wired) — see Common Pitfalls #2 for why these are two different security models sharing one DB column.

### Anti-Patterns to Avoid

- **Fixing the `dropitx-api` bugs found during this research from the frontend repo.** REQUIREMENTS.md's Out-of-Scope table explicitly excludes "Rewriting the FastAPI backend." The `profiles.py` UUID/TEXT mixup and `provision_firebase_user`'s ambiguous-column bug (already documented and fixed in `dropitx-api`'s own Phase 2 research) are real, but they're cross-repo — flag them in the plan's risk section, do not silently patch sibling-repo Python from this frontend phase.
- **Assuming path-only fixes for API-02.** Both `/api/v1/profile` and `/api/v1/favorites` require an architectural decision (see Open Questions), not a find-and-replace.
- **Treating "Publish" and "`/api/v1/documents`" as the same feature.** They're parallel, differently-authenticated paths (JWT-editor vs. API-key/CLI) that happen to do similar things. API-05 is a confirm-only task for Publish; do not attempt to merge or dedupe the two flows without an explicit user decision.

## Common Pitfalls

### Pitfall 1: Assuming `/api/v1/favorites` is a typo'd path

**What goes wrong:** A plan that just swaps the URL string will fail, because there is no `/api/v1/favorites`-shaped concept in the backend at all — not under any version prefix, tag, or router file.
**Why it happens:** The 404 *looks* like a versioning mismatch (frontend calling `/api/v1/...` for something backend only exposes unversioned), which is true for some endpoints in this codebase but not this one.
**How to avoid:** Confirmed via `grep -ril "favorite" app core models` in `dropitx-api` → zero matches `[VERIFIED: grep executed this session against dropitx-api/app, dropitx-api/core, dropitx-api/models]`. The nearest functional equivalent is Stars (`app/public/stars.py`), which is a **different table** (`share_stars`, keyed `share_id`+`user_id`) than the frontend's existing `favorites` table (queried directly in `app/(dashboard)/dashboard/favorites/page.tsx:32-34`, `.from("favorites").select("share_id, created_at, shares(*)").eq("user_id", user.uid)`). Treat this as a data-model decision (Open Questions #1), not a path fix.
**Warning signs:** If the plan for API-02 has only one task ("swap the path string"), it's under-scoped — favorites necessarily touches at least two files (`bookmark-toggle.tsx` AND `favorites/page.tsx`) if the Stars-migration path is chosen.

### Pitfall 2: Conflating "Encryption" (`/api/encryption/*`) with the existing "set-password"/"unlock" flow

**What goes wrong:** Building the encryption wiring as if it replaces `share-password-form.tsx`/`password-gate.tsx`, breaking the existing (already-working) password-gate feature.
**Why it happens:** Both flows write to the *same* `shares.password_hash` column (confirmed: `app/public/encryption.py:230` sets `password_hash` as a side effect of `/encrypt`), so on the surface they look like the same feature with two implementations.
**How to avoid:** They are different security models. `set-password`/`unlock` (existing, wired) is a **server-side gate only** — content is stored in plaintext server-side; the password just checks access. `/api/encryption/*` (new, unwired) **actually encrypts the content at rest** with a key derived from the password (or a random key) that never reaches the server — zero-knowledge. A share can be password-gated without being encrypted, but `/encrypt` sets both fields, meaning a plan must decide (and the user should confirm) whether "password-protect" in the UI should mean the cheap gate (current) or true encryption (new), or whether both remain available as distinct actions.
**Warning signs:** If `password-gate.tsx`'s unlock flow silently stops decrypting content after this phase, the encryption wiring was built as a replacement instead of an addition.

### Pitfall 3: `GET /api/u/{username}` and `/shares` will return zero share stats even when correctly wired (backend bug, cross-repo)

**What goes wrong:** After wiring the Public Profiles UI, every profile page will show `share_count: 0, total_views: 0, total_stars: 0` and an empty shares list, for every user, always.
**Why it happens:** `app/public/profiles.py:81-98` and `:144-148` select `id` from `user_profiles` (a random UUID PK per `infra/init/01_schema.sql:299`) and then use that value to filter `public_shares.eq("user_id", ...)` — but `public_shares.user_id` (via `shares.user_id`) is the Firebase-uid `TEXT` value, which lives in `user_profiles.user_id`, a *different column*, not `id`. `[VERIFIED: dropitx-api/app/public/profiles.py:81-82,144-148, read this session; dropitx-api/infra/init/01_schema.sql:298-310, read this session — "id UUID PRIMARY KEY DEFAULT gen_random_uuid()," / "user_id TEXT NOT NULL UNIQUE REFERENCES auth.users(id)"]`
**How to avoid:** This is a `dropitx-api` bug, out of this phase's edit scope (backend rewrite excluded per REQUIREMENTS.md). Flag it explicitly in the plan as a known limitation/blocker for API-04's "view a public profile page" success criterion, and surface it to the user as a cross-repo issue to file — do not attempt a silent fix in the sibling repo without an explicit go-ahead.
**Warning signs:** Manual QA of the new profile page shows a real user with real public shares reporting 0 shares/0 views.

### Pitfall 4: `/api/shares/{slug}/reencrypt` has no auth dependency at all

**What goes wrong:** Anyone who knows a share's slug and its *old* password can re-encrypt it with a *new* password, locking out the original owner — `reencrypt_share` (`app/public/encryption.py:264`) has no `Depends(get_current_user)`/`get_optional_user` in its signature, only rate limiting.
**Why it happens:** Likely an oversight given `encrypt_share` (the sibling endpoint) does check ownership via `authorize_owner`.
**How to avoid:** Not a fix for this phase (security hardening is Phase 3 scope) — but flag it in the plan's risk notes so it isn't silently wired into production UI without at least a `checkpoint:human-verify` acknowledging the gap, since wiring the encryption UI in this phase gives it a real, reachable entry point for the first time.
**Warning signs:** None visible from the frontend — this is a backend code-read finding only, worth a one-line callout in the plan.

## Open Questions

1. **Favorites: migrate to Stars, or build a frontend-native favorites write-path?**
   - What we know: The dashboard's existing `favorites` table (queried directly via Supabase in `app/(dashboard)/dashboard/favorites/page.tsx`) has no corresponding backend write endpoint anywhere. The backend's fully-built `Stars` feature (`share_stars` table + `/api/shares/{slug}/star`) is functionally identical (per-user, per-share, toggleable, with a count) but is a *different table*.
   - What's unclear: Whether the product intent is "one unified starred-shares concept" (migrate `favorites/page.tsx` to read `share_stars` via the Stars API, retire the standalone `favorites` table) or "keep favorites as a frontend-native concept with its own write path" (add a new Next.js Route Handler, e.g. `app/api/favorites/route.ts`, using `createAdminClient()` to write to the existing `favorites` table directly — architecturally consistent with the existing `app/api/shares` access-cookie route precedent, and requires zero `dropitx-api` changes).
   - Recommendation: Migrating to Stars is lower-total-effort (reuses tested, deployed backend code) and matches REQUIREMENTS.md's framing ("fixed to match the live API contract"). Surface both options to the user with this tradeoff before committing a plan; do not default silently.

2. **Profile display-name editing: new FastAPI endpoint (cross-repo) or new Next.js Route Handler (frontend-only)?**
   - What we know: No backend endpoint updates `user_profiles`. `ProfileForm.handleSave()` runs client-side and cannot write to Supabase directly (no admin credentials in the browser); a server-side write path is required either way. The frontend already has architectural precedent for its own server-side write routes (`app/api/shares` access-cookie routes, per this repo's CLAUDE.md).
   - What's unclear: Whether adding one small write endpoint to `dropitx-api` counts as "rewriting the FastAPI backend" (REQUIREMENTS.md's stated exclusion) or is acceptable as a minimal, scoped addition; this is a judgment call only the user can make given the exclusion's wording is ambiguous on scale.
   - Recommendation: A Next.js Route Handler (`app/api/profile/route.ts` using `createAdminClient()`) fully avoids the cross-repo question and is buildable entirely within this phase's stated boundaries — recommend this as the default unless the user explicitly wants profile writes centralized in the backend for consistency with other user-scoped writes.

3. **`/api/upload/batch` and `GET /api/shares/{slug}/files`: this phase (API-05) or Phase 4's FEAT-03 (multi-file backend wiring)?**
   - What we know: `/api/upload/multi` (single share, multiple files) is already wired. `/api/upload/batch` (multiple *independent* shares uploaded together, returning a `group_slug`) is a distinct, unwired feature pairing with the already-registered `GET /api/download/group/{slug}` bulk-zip endpoint. `GET /api/shares/{slug}/files` (listing files within one multi-file share) is also unwired and overlaps conceptually with FEAT-03's "multi-file organization" UI, which ROADMAP.md scopes to Phase 4.
   - What's unclear: Whether wiring `/upload/batch` belongs in this phase (API-05 explicitly names "batch/multi/image upload" as in scope) versus deferring the `files`-listing endpoint to Phase 4 to avoid duplicate work.
   - Recommendation: Wire `/upload/batch` in this phase (API-05 names it explicitly); defer `GET /api/shares/{slug}/files` to Phase 4 since FEAT-03's stated backend-wiring scope is a closer match — note this split explicitly in the plan so Phase 4's research doesn't re-discover the same endpoint as if it were still fully unaddressed.
