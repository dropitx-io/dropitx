<objective>
Wire the encryption endpoint group (API-04). This is the phase's most subtle piece: `lib/crypto.ts` already implements the exact AES-256-GCM / PBKDF2 / URL-fragment-key contract `/api/encryption/*` expects, and has simply never been called. The work is a UI surface plus correct call sequencing — not new cryptography.

Purpose: encryption is the only backend capability in this phase where a wrong implementation causes silent, unrecoverable data loss (an owner locked out of their own content). It is also the one that first exposes a known unauthenticated backend endpoint to real users.
Output: an `EncryptShareDialog` mounted alongside — never replacing — the existing password gate, behind a blocking human acknowledgement of the re-encrypt authorization gap.
</objective>

  <name>Task 1: Acknowledge the unauthenticated reencrypt_share gap before building the encryption UI</name>
  <what-built>Nothing yet — this checkpoint runs FIRST, before any encryption UI exists, because approving it is what authorizes building the UI at all.

Research verified (`dropitx-api/app/public/encryption.py:258-264`, read directly) that `POST /api/shares/{slug}/reencrypt` has **no authorization dependency of any kind** in its signature — no `Depends(get_current_user)`, no `Depends(get_optional_user)`, only rate limiting. Its sibling `encrypt_share` does check ownership via `authorize_owner`. The consequence: anyone who knows a share's slug and its *current* password can re-encrypt it under a new password of their choosing, permanently locking out the original owner.

This gap exists in production today. What changes in this phase is reachability: wiring the encryption UI gives it its first real, discoverable entry point. That is a material change in exposure even though no line of backend code moves.

Fixing it is explicitly out of scope here — it is `dropitx-api` code, and REQUIREMENTS.md excludes "Rewriting the FastAPI backend"; security hardening is Phase 3. CONTEXT.md's decision is to flag, not fix — but not to ship silently either.</what-built>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/api/shares/{slug}/encrypt` | Owner-authorized; the password crosses here, the derived key does not |
| browser -> `/api/shares/{slug}/reencrypt` | **No authorization boundary exists server-side** — only rate limiting |
| URL fragment -> server | The fragment is never transmitted by the browser; this is the mechanism that makes the design zero-knowledge |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.1-01 | Elevation of Privilege | `POST /api/shares/{slug}/reencrypt` (`dropitx-api/app/public/encryption.py:258-264`, no auth dependency) | high | transfer + mitigate | The backend fix is out of scope (cross-repo, Phase 3 / REQUIREMENTS.md excludes backend rewrites). Transferred to `dropitx-api` via a filed cross-repo note. Mitigated here by the **blocking human checkpoint in Task 1**, which is not auto-approvable, plus the mandatory verbatim destructive-confirmation copy required before submit. Shipping this UI without the checkpoint is prohibited. |
| T-01.1-02 | Repudiation / Tampering | conflating "Set Password" with "Encrypt This Share" | high | mitigate | The two are different security models sharing one `shares.password_hash` column: set-password is a server-side access gate over plaintext content; encrypt actually encrypts content at rest with a key the server never sees. Collapsing them silently downgrades or breaks a shipped guarantee. Mitigated by the prohibition, the distinct-icon rule (`Lock` vs `ShieldCheck`), and the acceptance criterion that `share-password-form.tsx` and `password-gate.tsx` are byte-unchanged. |
| T-01.1-17 | Information Disclosure | encryption key / password material in the client | high | mitigate | Key material lives only in the URL fragment via `lib/crypto.ts`'s `setKeyInFragment`. Prohibited from `localStorage`, `sessionStorage`, logs, and any request body; enforced by the acceptance criterion grepping for those three. `lib/crypto.ts` is byte-unchanged (`git diff --quiet`), so the PBKDF2 parameters and AES mode stay matched to the backend's `core/encryption.py`. |
| T-01.1-18 | Denial of Service (owner lockout) | a failed or partial encrypt | medium | mitigate | On any non-OK response the dialog stays open, surfaces the mandatory "Your content was not changed." copy, and presents no partial-encryption state. The backend performs the state transition atomically; the frontend never writes IV/salt itself. |
| T-01.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs nothing — the dialog reuses `components/ui/dialog.tsx` and `components/ui/input.tsx`. `git diff --stat package.json package-lock.json` must be empty; if it is not, HALT (no legitimacy audit entry exists for any new package). |
